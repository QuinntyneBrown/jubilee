Inline message

Inline messages sit next to the thing they describe: help under a label, an error under the field that caused it, "Saved at 9:33 a.m." beside the form it saved. They are text first; colour and the dot only reinforce it.

Overview

Use these for feedback scoped to one control or one form. For a message about a whole section, use an Alert and banner; for an outcome the person might miss, a Toast. The field wrapper and label are documented in Form field.

  • Help (.field__help): what to enter and why, in muted text, between label and control.
  • Error (.field__error): how to fix the value, in danger text with a warning glyph, below the control; the control gets aria-invalid="true".
  • Inline status (.inline-status): a live save status for a form or settings list: idle, saving, saved, failed.
  • Dot (.dot): an 8px currentColor dot that leads an inline status; .dot--pulse while saving. Always beside text, never alone.

Anatomy

  1. LabelFrom the form field; the message never repeats it.
  2. Help--text-body-sm, --color-fg-muted, linked by aria-describedby.
  3. Invalid controlaria-invalid="true": danger border plus an inset hairline, so the state does not rely on colour alone.
  4. Error--text-body-sm, --color-danger-fg, warning glyph, linked by aria-describedby after the help.

  • Errors appear on submit or on leaving a field the person has changed, never while they are still typing the first time.
  • An error clears as soon as the value becomes valid; the help stays.
  • A failed save keeps the person's input and offers a retry in the nearest alert or toast.

Responsive behaviour

  • Messages wrap under the control at every width; they never sit beside it, so 360px phones need no special layout.
  • In a form footer the inline status takes its own row above the buttons when the row wraps.

Theming

Help reads --color-fg-muted, error --color-danger-fg, the status tones --color-success-fg and --color-danger-fg. All flip in the dark theme through the semantic tier; the dot is currentColor so it always matches its text.

Accessibility

Role and pattern

Help and errors are plain text linked to the control with aria-describedby (help id first, then error id); the control carries aria-invalid="true" while in error. The save status is one role="status" live region. See the APG names and descriptions practice and WCAG 3.3.1 Error identification.

Keyboard

KeyAction
TabMessages are not focusable; they are read with the control as its description.
Error summary linkMoves focus to the invalid control, which then reads its error.

Focus

No focus of its own. After a failed submit, focus goes to the error summary, not to the first error.

Labelling

The label names the field; help and error describe it. Do not put the error in the label or in placeholder. The warning glyph is CSS content and should be silent: see the drift note.

Motion

The saving dot pulses over --duration-loop; reduced motion stops the pulse and keeps the text "Saving…".

Touch

Not interactive. Messages never shrink the control's 44px height.

Content

  • Errors say how to fix: "Enter a 10-digit phone number, like 416-555-0142". Not "Invalid phone".
  • Give the example in the help or the error, in Canadian format: postal code M4C 1A1, phone 416-555-0142, prices like 24.00.
  • Help says why we ask when it is not obvious: "Shared with Luzandre.com for this request only."
  • Status uses the clock time: "Saved at 9:33 a.m.", not "Saved just now".

Extracted from these mocks:

  • dialogs/order-request/invalid (field errors in a dialog)

Drift fixed during extraction: help sits before the control but in the sign-up password field the error is rendered before the help and aria-describedby lists help first, so visual and spoken orders differ; the system puts help between label and control and the error after the control. The redrawn Sign up (ADR 0038) is the one exception: its hints sit under the control in every state, with an error between the two. The two .dot spans in the preferences mocks lack aria-hidden. The footer "Saving…" status in account and edit-listing has no role="status", and every footer status uses style="margin-right: auto"; a .form-actions .inline-status { margin-inline-end: auto; } rule would replace it. .field__error::before { content: "⚠" } is read aloud as "warning sign" by some screen readers; content: "⚠" / "" silences it.
