# 0049. Finish joining: the unconfirmed address in a dialog, the resend limit shown, tokens out of the logs

Status: accepted

## Context

Journey 4 (join Jubilee) left three criteria open. "Use another e-mail" on the waiting page and "Change e-mail" on the verify-e-mail banner led to the account page, where the only change of address asks for a password and waits for a link, so no screen called `PUT /api/account/unconfirmed-email` (L2-004 AC5). The resend limit answered 429 and the member was told nothing (L2-005 AC5). The request log wrote request paths in full, and two paths carry a token: the data download and the one-click unsubscribe (L2-140 AC3). A fourth, the `__Host-` prefix of the member cookie (L2-135 AC1), was settled by journey 5 in ADR 0046 while this work was under way, and is not decided again here. The confirm e-mail design named an `ILinkTokenRedactor` and a `RateLimitMiddleware` that were never built.

## Decision

- **The unconfirmed address is changed in a dialog of its own, `ChangeUnconfirmedEmailDialog`, titled "Use another e-mail".** It is opened from the waiting page and from the banner, and asks for the address only. There is no password: the address is not proven yet, so the session is the only proof there is, and a member who joined with a typo must not need the link they cannot receive. The dialog of the account page (`ChangeEmailDialog`, L2-014) stays for a confirmed address; its rules (password, the old address kept until the link is opened) do not fit, so the two are not merged. Its mocks are the `unconfirmed*` states of `dialogs/change-email/`.
- **An address in use is said from the session, not from the answer.** `PUT /api/account/unconfirmed-email` answers 204 whether or not the address belongs to someone (L2-141 AC1) and tells the holder by e-mail. The member's own session already says which address they have, so the dialog reads the session after the 204: when the address is the new one it shows "Check your new inbox"; when it is not, the field says "An account already uses this e-mail. Use another address." The endpoint's answer does not change. A member learns no more than the join form already tells a visitor (L2-002 AC1), and only 5 times an hour.
- **The limit is said in the words the join form uses.** A 429 from the resend or the change shows "You’re doing that a lot. Try again in {n} minutes.", with the minutes of `Retry-After`: in the banner (a new `limited` state, warning tone, with no "Send it again" until the page is loaded again), on the waiting page and in the dialog. Resends and changes share one budget of 5 an hour per member (`AccountRateLimit.Resends`); the limiter is ASP.NET Core's, there is no `RateLimitMiddleware`.
- **"Change e-mail" in the banner is a button.** It opens a dialog and goes nowhere, so it is a `button` (link variant in the persistent state, small button in the bounced state) and the banner raises `changeEmail`. The mocks changed first.
- **Tokens are kept out of the logs where the path is written, by `LoggedPath`.** Every log line that names the request path (the request log, the failed-authorization lines, the error lines) writes `LoggedPath.Of(context)`: the value of a route parameter named `token` is replaced by `[redacted]`, and where no route was matched (a 404 or a 405) any path segment of 40 characters or more is. Confirmation, reset and e-mail-change tokens travel in request bodies, which are never logged; the query string is never logged; the session cookie is never logged. A route that carries a token names the parameter `token`. There is no `ILinkTokenRedactor` service: one static function is all the three call sites need, and ASP.NET Core's own request logging stays at `Warning`.

## Consequences

- A slug or other path segment of 40 characters or more on an unmatched path is logged as `[redacted]`. Matched routes are logged in full, apart from their token.
- The `limited` banner state is not remembered: a reload shows "Send it again" again, and pressing it within the hour shows the limit again.
- The session cookie is never logged under either of its names (ADR 0046): `TokenRedactionTests` reads the log after a join and a sign-in.
- Checked while this was built, on 12 November 2026: Chromium keeps a `Secure` `__Host-` cookie set from `http://localhost` through the development proxy. ADR 0046 gives the Development environment an unprefixed cookie because browsers refuse the prefix over plain HTTP; for Chromium that exception is not needed. It is left as ADR 0046 decided, because other browsers do refuse it.
- Still open, and outside this journey: a CSP on the SPA host and the TLS redirect (`docs/detailed-designs/security/`). Reopening the action a visitor was attempting after joining was built by journey 5 (ADR 0046).
