# L2 - Detailed Requirements

Each requirement traces to exactly one L1 in [L1.md](L1.md), and every L1 traces to the mission,
L0-001 in [L0.md](L0.md). Acceptance criteria are written in
Given/When/Then form so each one becomes an acceptance test. Mock references (`mock:` lines) point
to the screens in `docs/mocks/` that show the requirement; the mocks' copy is the default product
copy.

**Conventions used in every requirement**

- "Member" means a signed-in account holder; "visitor" means not signed in; "owner" means the
  member who owns the listing in question; "Jubilee team" means a staff account with the
  `moderator` role. A "staff session" is the session of a staff account in the admin application
  (L2-190); a "member session" is the session of L2-010.
- Viewport classes: XS < 576px, SM >= 576px, MD >= 768px, LG >= 992px, XL >= 1200px. Acceptance
  tests for responsive criteria run at 360, 576, 768, 992 and 1280 px wide. The mocks' own layout
  breakpoints are 640 px (40rem), 768 px (48rem) and 1024 px (64rem); where a criterion names one
  of those, it is the exact switch point.
- All times are shown in the America/Toronto time zone in en-CA format (for example
  "Thu 12 Nov, 10:00 a.m."). All money is Canadian dollars.
- "Error reference" means a code of the form `JB-<AREA>-<NNN>` shown to the user and logged with
  the request's correlation ID (see L2-118).

## L2-001: Join with e-mail and password
**Traces to:** L1-001

A visitor creates an account at `/join`, the Sign up screen, with first name, last name, e-mail,
password, an optional home church and its optional address, and agreement to the statement of faith and terms. A Google
option is offered first on the same page (L2-003). On success the account is created unconfirmed
and a confirmation e-mail is sent. The layout of the screen is L2-187.

mock: `pages/sign-up/*`

**Acceptance Criteria:**
1. Given a visitor on `/join`, when they enter first name "Joanna", last name "Adeyemi", e-mail "joanna.adeyemi@example.com", a 13-character password, tick the agreement and press "Create account", then an account is created with e-mail status "unconfirmed" and the page shows "Check your e-mail" naming the address and stating the link must be opened within 24 hours.
2. Given the success state, when the visitor presses "Send it again", then a new confirmation e-mail is sent and any earlier link for that account stops working.
3. Given the join form, when it is shown, then it has "First name", "Last name", "Email" (placeholder "you@example.com"), "Password" (hint "At least 10 characters.") and "Home church", marked "(optional)", with the placeholder "e.g. The Meeting House" and the hint "Shown to no one. Helps us recommend businesses near you.", followed by "Home church address", marked "(optional)", with the placeholder "e.g. 2700 Bristol Circle, Oakville" and the hint "Shown to no one." (L2-196); the four other fields are required and carry no marker.
4. Given the agreement checkbox "I am 18 or older and agree to Jubilee’s statement of faith and terms.", when it is shown, then "statement of faith" links to `/statement-of-faith` and "terms" links to `/terms`, both opening without losing typed form values.
5. Given a successful join, when the account is created, then the stored e-mail is normalised (trimmed, domain lower-cased) and the password is never stored or logged in plain text.
6. Given a visitor who is already signed in, when they open `/join`, then they are redirected to `/`.
7. Given a visitor on `/join`, when the form is shown, then the heading is "Join Jubilee" with "Free for everyone in Toronto’s Christian community." under it, and below the form "Already on Jubilee?" offers "Log in" linking to `/sign-in`.
8. Given 640 px or wider, when the form is shown, then "First name" and "Last name" sit side by side; given 1024 px or wider, then "Email" and "Password" sit side by side as well; below those widths each pair is stacked.

## L2-002: Join form validation
**Traces to:** L1-001

The join form validates on submit, in the browser and again on the server, and reports every
problem at once.

mock: `pages/sign-up/invalid.html`

**Acceptance Criteria:**
1. Given an e-mail that already belongs to an account, when the visitor submits, then the field shows "An account already uses this e-mail. Log in instead, or use another address." and no second account is created.
2. Given a password of 5 characters, when the visitor submits, then the field shows "Use at least 10 characters. This one has 5."
3. Given the agreement is not ticked, when the visitor submits, then the checkbox shows "Agree to the statement of faith to join." and no account is created.
4. Given three invalid fields, when the visitor submits, then a summary titled "Fix 3 things to continue" appears above the form listing each problem as a link to its field, and focus moves to the summary.
5. Given a first or last name longer than 50 characters, or an e-mail longer than 254 characters, or a password longer than 128 characters, when submitted, then the server rejects it with a field error and the browser limits input to that length.
6. Given any invalid submission, when the errors show, then every value typed (except the password) is kept.
7. Given a request that bypasses browser validation, when the server receives invalid data, then it responds 422 with per-field error codes and creates nothing.

## L2-003: Continue with Google
**Traces to:** L1-001

Visitors can join or sign in with Google using OpenID Connect.

mock: `pages/sign-in/default.html`, `pages/sign-up/default.html`, and the `google-*` states of both

**Acceptance Criteria:**
1. Given a visitor with no account, when they choose "Sign up with Google" and consent, then an account is created from the Google name and verified e-mail, marked e-mail "confirmed", and the visitor is shown the statement-of-faith and terms agreement before the account becomes usable.
2. Given a member who joined with e-mail and confirmed it, when they choose "Continue with Google" with the same verified e-mail, then the Google identity is linked to the existing account and they are signed in.
3. Given a Google sign-in, when the callback arrives, then the `state` and `nonce` values are verified and PKCE is used; a mismatch rejects the sign-in and shows the sign-in error state.
4. Given a Google account whose e-mail is not verified by Google, when it is used, then sign-in is refused with "Use a Google account with a confirmed e-mail, or join with e-mail."
5. Given Google sign-in is not configured, when a visitor opens `/join` or `/sign-in`, then "Sign up with Google" and "Continue with Google" are not shown, nor the "or use email" divider under them, and no request leaves for Google; and given a request to start a Google sign-in all the same, then the visitor is returned to where they started with the sign-in error state.
6. Given a visitor who cancels at Google, when they return, then they are back on the page they started from (`/join` or `/sign-in`) with "You didn’t finish with Google. Try again, or use your e-mail and password.", and the place they were going to is kept.
7. Given a Google sign-in started from `/join` that fails or is refused, when the visitor returns, then the message of criterion 3 or 4 is shown on `/join`, not on `/sign-in`.
8. Given Google sign-in is configured, when `/join` or `/sign-in` is shown, then the Google button comes first, above the form, and carries the Google "G": "Sign up with Google" on `/join` and "Continue with Google" on `/sign-in`; a divider reading "or use email" separates it from the form.
9. Given `/join` or `/sign-in` opened while the app's request for the session went unanswered (as while Jubilee starts after a deployment), when it is shown, then the Google button and the divider are not shown yet, as in criterion 5, and the app asks for the session again after 5, 10, 20, 40 and then every 60 seconds until it is answered; and given an answer that says Google sign-in is configured, then the Google button and the "or use email" divider appear as in criterion 8 without the visitor reloading the page, and what the visitor has typed is kept.

## L2-004: E-mail confirmation link
**Traces to:** L1-001

A confirmation link at `/verify-email/:token` confirms the member's e-mail. It works once, for 24
hours.

mock: `pages/verify-email/*`, `notifications/verify-email-banner/*`, `dialogs/change-email/unconfirmed*.html`

**Acceptance Criteria:**
1. Given a valid unused link younger than 24 hours, when the member opens it, then the page shows "Confirming your e-mail…" and then "E-mail confirmed" with "Start browsing" and "List your business", and the account's e-mail status becomes "confirmed".
2. Given a link older than 24 hours, when opened, then the page shows "This link has expired" with "Send a new link", and the account stays unconfirmed.
3. Given a link already used, when opened again, then the account is not changed and the page shows the success state if the account is confirmed, otherwise the expired state.
4. Given a token that does not exist or is malformed, when opened, then the expired state is shown and no information about any account is revealed.
5. Given the "Confirm your e-mail" waiting page or the banner of L2-005, when the member presses "Use another e-mail" or "Change e-mail", then a dialog titled "Use another e-mail" asks for the new address and no password; when it is sent, the address replaces the unconfirmed one, earlier links stop working, a new link goes to the new address, the dialog shows "Check your new inbox" naming it, and the page and the banner name the new address.
6. Given a confirmation e-mail that bounces, when the bounce is received, then the member sees the danger banner "We couldn't deliver e-mail to {address}. Check the address for a typo." with "Change e-mail".
7. Given the check cannot complete because of a server or network failure, when the page loads, then it shows "We couldn't load your verification" with error reference `JB-VERIFY-502` and "Try again".
8. Given the dialog of criterion 5, when the address is empty or is not a full e-mail address, then nothing is sent and the field says "Enter the e-mail you want to use." or "Enter a full e-mail address, like name@example.com."; while the address is being sent the button reads "Sending…" and the dialog cannot be closed.
9. Given the new address already belongs to another account, when it is sent, then the API answers as it does for any other address (L2-141 criterion 1), the unconfirmed address is not replaced, the holder is told by e-mail that someone tried to use their address, and the field shows "An account already uses this e-mail. Use another address."
10. Given the member has reached the limit of L2-005 criterion 5, which changes of address and resends share, when the address is sent, then nothing changes and the dialog says "You’re doing that a lot. Try again in {n} minutes."

## L2-005: Restrictions on unconfirmed members
**Traces to:** L1-001

Until the e-mail is confirmed, a member can browse, search and save but cannot message, book,
request or list a business.

mock: `notifications/verify-email-banner/persistent.html`, `pages/notifications/default.html`

**Acceptance Criteria:**
1. Given an unconfirmed member, when they view any signed-in page, then a persistent banner shows "Confirm your e-mail to message businesses. We sent a link to {address}." with "Send it again" and "Change e-mail", and it has no dismiss button.
2. Given an unconfirmed member, when they try to send a message, booking, quote or order request, or publish a listing, then the action is blocked in the UI and the API responds 403 with code `EMAIL_UNCONFIRMED`.
3. Given an unconfirmed member, when they save a business, then the save succeeds.
4. Given the member confirms their e-mail in another tab, when the original tab regains focus, then the banner changes to the success state "E-mail confirmed. You can now message businesses and book meetings." and the blocked actions become available without reload.
5. Given an unconfirmed member presses "Send it again" more than 5 times in an hour, when they press it again, then the API answers 429 with `Retry-After`, no e-mail is sent, and the banner or the waiting page says "You’re doing that a lot. Try again in {n} minutes." with the wait the API named.

## L2-007: Sign-in throttling and lockout
**Traces to:** L1-001

Repeated failed sign-ins are slowed and then temporarily blocked to stop password guessing.

**Acceptance Criteria:**
1. Given 5 failed sign-ins for one account within 15 minutes, when a sixth attempt is made, then it is refused for 15 minutes with "Too many tries. Wait 15 minutes or reset your password." regardless of whether the password is right.
2. Given 20 failed sign-ins from one IP address across any accounts within 15 minutes, when another attempt is made from that address, then it is refused with HTTP 429 and a `Retry-After` header.
3. Given an account is temporarily locked, when the lock starts, then the account holder is e-mailed that sign-in was blocked after repeated failures, with a link to reset the password.
4. Given a successful sign-in, when it happens, then the failed-attempt counter for that account resets.

## L2-008: Forgot password
**Traces to:** L1-001

## L2-010: Session lifetime
**Traces to:** L1-001

Sessions are server-side, last up to 30 days when "Keep me logged in" is ticked, and end when the
password changes.

mock: `pages/sign-in/default.html`, `pages/session-expired/default.html`

**Acceptance Criteria:**
1. Given "Keep me logged in" is ticked, when the member signs in, then the session lasts 30 days from sign-in and survives closing the browser.
2. Given "Keep me logged in" is not ticked, when the member closes the browser, then the session ends, and in any case it ends after 12 hours without activity.
3. Given a session older than 30 days, when the member makes any request, then they are sent to `/session-expired`, which shows "You've been signed out. For your safety we sign you out after 30 days, or when your password changes." and "Sign in".
4. Given a session ends while the member has an unsent message or form draft, when they sign in again as the same member, then the draft is restored (L2-116).
5. Given a member signs in, when the session starts, then a new session identifier is issued (no session fixation).

## L2-017: Delete account
**Traces to:** L1-002

A member permanently deletes their account after typing DELETE.

mock: `dialogs/delete-account/*`

**Acceptance Criteria:**
1. Given the member presses "Delete my account", when the dialog opens, then it names the account (name and e-mail) and states what happens with live counts: "Your profile, saved list and {n} conversations are deleted. Your {n} open requests are cancelled and the businesses are told. This can't be undone."
2. Given the confirmation field contains anything other than exactly "DELETE", when "Delete account" is pressed, then the field shows "Type DELETE in capital letters to confirm." and nothing is deleted.
3. Given "DELETE" is typed, when confirmed, then the account is deleted, every session ends, open requests are cancelled with the businesses notified, the member lands on `/welcome` with a confirmation toast, and a confirmation e-mail is sent. Nothing the member saw or wrote stays on the device: the saved pages, the outgoing queue and the member’s drafts are cleared (L2-119 AC3, L2-116 AC4).
4. Given the member owns a listing, when the account is deleted, then the listing is unpublished and removed from browse and search immediately.
5. Given the deletion fails, when the error returns, then the dialog shows "We couldn't delete your account. Nothing was removed. Try again, or write to help@jubilee.example." and keeps the typed confirmation.
6. Given an account has been deleted, when 30 days pass, then all of its personal data is erased from primary storage, and from backups within 35 days of deletion; messages the member sent remain visible to the business as from "Former member". The personal data erased includes the profile, the sessions with their device and network, consents and statement-of-faith agreements, password-reset requests, queued e-mails, export archives, the photos of the member’s listings and products, the phone and delivery address of the member’s requests, and the member’s name on the listing reports they sent. Backups of the database are kept 35 days or less (an owner setting), so no backup holds the data later than 35 days after deletion.
7. Given the database is restored from a backup taken before an account was deleted, when the worker next starts or makes its hourly pass, then the deletion is re-applied from the deletion ledger, which is kept outside the database and holds only the account’s id and the time of deletion: nothing can sign in to the account, its open requests are cancelled without telling the businesses again, its listings are unpublished, and its erasure follows 30 days after the original deletion. Every deletion is written to the ledger when it is made, and a deletion the ledger is missing is written to it on the next pass.

## L2-018: Download your data
**Traces to:** L1-002

As stated on the privacy page, a member can download their data.

mock: `pages/privacy/default.html`, `pages/account/data-requested.html`, `pages/account/data-failed.html`, `pages/account/data-build-failed.html`, `pages/data-download/*`

**Acceptance Criteria:**

## L2-138: File upload security
**Traces to:** L1-019

**Acceptance Criteria:**
1. Given an upload (listing photo, product photo, message photo), when received, then the server checks the content type by its magic bytes, accepts only JPEG and PNG up to 5 MB and 8,000 × 8,000 pixels, re-encodes the image, and strips metadata.
2. Given uploads, when stored, then they are kept in object storage outside the web root with random names, scanned for malware, and served from a separate cookieless domain with `Content-Type` fixed and `X-Content-Type-Options: nosniff`.
3. Given a file that fails any check, when uploaded, then it is rejected and never served.
4. Given a message photo that passed the checks of AC1, when it is uploaded, then it is given to the malware scanner before it is stored: a photo the scanner calls infected is refused with HTTP 422 and code `FAILED_SCAN`; when no scanner is configured, or it does not answer within its time limit, the photo is refused with HTTP 503 and code `SCAN_UNAVAILABLE`. In both cases nothing is stored and nothing can be served. Only a development machine and the e2e API run without a scanner (`Malware:Scanner` set to `none`), and the API says so in its log when it starts.
5. Given a message photo, when it is stored, then its bytes are kept by the media store, outside the web root and the database, under a random name of 128 bits that holds nothing of the file's own name, and it is reached only through the signed link of L2-060 AC4.
6. Given a product photo that passed the checks of AC1, when an owner uploads it to `POST /api/my-business/products/photos`, then it is given to the malware scanner before it is stored, as AC4 says (422 `FAILED_SCAN`, 503 `SCAN_UNAVAILABLE`, nothing stored); a clean photo is kept as renditions under a random name of 128 bits and served publicly under `/media` like a listing photo. A product takes only a photo its own owner uploaded (another owner's photo is 422 `photo` `INVALID`), and an owner uploads at most 30 product photos an hour (429 `rate_limited`).
